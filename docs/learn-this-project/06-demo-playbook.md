# Demo Playbook — `learn_sql_query_basic`

> How to demo this course effectively. Honest, audience-tailored. The course is a teaching artifact, not a product — the right demo emphasizes *the teaching design* and *the curriculum coherence*, not the codebase.

## Wow features (the 1–3 strongest things to show)

1. **The lesson-folder template — one lesson = one industry = one DB.**
   - What it is: every lesson folder is self-contained — README (bilingual) → CSV seeds → committed `db.sqlite` → bilingual SQL files with `Business question` / `Why this query` headers. Once you've seen one, you've seen them all.
   - Why it lands: the uniformity is the curriculum's UX. A demo viewer who's ever tried to learn from a tutorial that re-invents its layout each chapter immediately gets why this matters.
   - File/URL to open: `examples/12-group-by/` is the canonical example. Open it in Finder/Explorer (or `tree` it in a terminal) to show the folder shape.
2. **The `Business question` + `Why this query` header convention.**
   - What it is: every `example_*.sql` opens with two comment blocks — the business question (in plain English: "which category keeps the register busiest?") and the rationale (the principle the SQL embodies). The SQL is below.
   - Why it lands: demonstrates the course's pedagogical stance — 知其然知其所以然 (know what AND why). Most SQL tutorials skip the "why".
   - File/URL to open: `examples/12-group-by/example_01.sql` (the simple case). Bonus: `examples/12-group-by/example_06.sql` for the "broken-version-in-comments → fixed-version-below" teaching shape.
3. **Per-industry variety + the curriculum dependency order.**
   - What it is: the 22 SQL lessons each use a different industry (bookstore → café → gym → hotel → cinema → streaming → podcast → delivery → library → bank → conv. store → fitness → vet → ride-share → concert → retail org chart → dating → subscription box → real estate → coffee → soccer → weather). The order is conceptual-dependency, not surface-difficulty (windows last, GROUP BY before JOINs, joins as 4 separate lessons).
   - Why it lands: shows the course was *designed*, not assembled. Curriculum design is the harder-to-fake teaching skill.
   - File/URL to open: `examples/README.md` — scroll through the table of contents.

## Audience tailoring

| Audience | Recommendation |
| :------- | :------------- |
| **Hiring manager, role *related* to data / SQL / teaching / dev-rel** | Use the 15-min sequence. Emphasize beats 5 (DB committed to git = friction-reduction instinct), 7 (broken example = pedagogy depth), and 10 (curriculum order = design thinking). |
| **Hiring manager, role *unrelated* to this domain** (e.g. a frontend role, an ML research role, a sales engineer role) | **Consider skipping this project entirely.** A SQL teaching course is a poor signal for an unrelated role and you risk burning bandwidth that should go to the more-relevant portfolio piece. If you must show something, use the 5-min sequence and frame it as "I built a teaching artifact end-to-end" rather than "I built a SQL course" — the meta-skill (curriculum design + content production + tooling) is the transferable signal. |
| **Peer engineer (technical interview / chat)** | Use the 15-min sequence but lean into the design rationale. Open with `csv_to_sqlite.py` (Q: "why Core not ORM?") and `check_examples.py` (Q: "why try-whole-file-first before splitting on `;`?"). They'll appreciate the tradeoff thinking more than the curriculum. |
| **Non-technical stakeholder** (potential collaborator, content partner, learner) | Use the 5-min sequence but skip beat 5's live DBeaver query (it's intimidating). Replace with "and here's the lesson on window functions" → open `examples/23-window-functions-aggregates/README.md` and read the first paragraph. Emphasize the user-visible value: a beginner who finishes this can read window-function SQL. |

> **Be honest about audience misfit.** If the role isn't a fit for this project, recommending you skip it is the *correct* call — and saying so up-front in the demo conversation ("I'll keep this short because it's not directly relevant to <role>, but the meta-skill is…") signals self-awareness, which always lands well.

## Recovery moves — what to say if a beat fails live

| Beat | Failure mode | Recovery |
| :--- | :----------- | :------- |

| 4 (header comment block) | File is on screen but the screen-share is laggy | "The two comment blocks above the SQL are the business question and the rationale — every example file is shaped this way." (Wait for screen to catch up; don't backtrack.) |
| 7 (broken example in lesson 12) | Viewer asks "but does this actually run?" | "Yes — the SQL below the comment block is the correct version. The harness runs the file as-is. I'll show:" run `python examples/check_examples.py | grep group-by` (if terminal is open). |
| 2 (folder file list) | Demo viewer asks "what's in `data/`?" | "One or more CSVs, prefixed `01_`, `02_` etc. The prefix orders FK-dependent loads — `01_pets.csv` before `02_visits.csv` in the join lesson, for example. Want me to open that lesson?" |
| 6 (lesson 01) | Viewer asks "why is the folder name different?" | Don't apologize. Say: "Historical — lesson 01 predates the hyphen convention used in 02 onward. The harness tolerates both via a regex. I left it because renaming would break any external bookmark." |
| Any beat | Viewer asks "but how do I know the SQL is right?" | "Today, the harness verifies it parses against the committed DB. Snapshot-based correctness tests are on the elevation roadmap — `docs/learn-this-project/03-elevation-roadmap.md`. I think it's the highest-priority next upgrade." |

## Rehearsal questions — what a viewer might ask

The demo skill uses these to drill the user in rehearsal mode.

1. "Why SELECT-only? Doesn't a real working SQL engineer need INSERT/UPDATE too?" → see `docs/learn-this-project/04-quiz-bank.md#Q-016`. Defend the scope; acknowledge the gap; point at the elevation roadmap's pedagogical-depth section.
2. "Why polars and not pandas?" → see `docs/learn-this-project/05-interview-playbook.md#Q3.1`. API clarity, not speed. Datasets are 10-200 rows.
3. "Who's the audience? Beginners can't open DBeaver; experts don't need lessons on SELECT." → audience is data analysts / data scientists / backend engineers learning to read and write basic-to-intermediate SQL. The bootstrap lesson 01 closes the "I can't open DBeaver" gap for the beginner end.
4. "Why bilingual? Doesn't it double maintenance?" → reaches Mandarin-speaking audience; maintenance cost is real and managed by lock-step editing. (For demo audiences who only read English, downplay this and frame as "an extension I chose to do".)
5. "What if I want to skip ahead to window functions?" → fine, but lesson 22 assumes comfort with PARTITION BY (sibling of GROUP BY, lesson 12) and ORDER BY (lesson 07). Suggest skimming those READMEs first.
6. "How long does the full course take?" → no official estimate. Honest answer: ~20-40 hours for a beginner working through all 23 lessons attentively, less for someone who already knows half the topics.
7. "What's missing?" → say it cleanly: schema design, writes, transactions, indexes/EXPLAIN, performance, cross-engine dialects, recursive CTEs, LATERAL joins, exercises with hidden goldens, CI. Then add: "The elevation roadmap (`docs/learn-this-project/03-elevation-roadmap.md`) covers what I'd build next."
