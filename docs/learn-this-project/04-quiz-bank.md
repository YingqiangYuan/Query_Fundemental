# Quiz Bank — `learn_sql_query_basic`

## How these questions are designed

The questions in this bank are **discussion prompts, not fill-in-the-blank**. They are calibrated for 知其然知其所以然 — the learner must demonstrate both *what* the answer is and *why* it's shaped that way.

1. Questions are open-ended. A learner cannot answer "the command is `mise run inst`" and pass — they must say *where they'd look* to confirm that command exists.
2. **A good answer is 3–5 sentences** that names file paths AND explains the underlying principle.
3. **If a question can be answered in one sentence, the question was too narrow** — split it open or merge it with a sibling.

### What good vs bad questions look like (preserve this in future regenerations)

- ❌ Bad: "What command creates the venv?" → forces recall of `mise run venv-create`. Pure memorization, teaches nothing.
- ✅ Good: "A new contributor asks how to get a working environment — where do you point them and what do you tell them about how the toolchain fits together?" → forces them to open `mise.toml`, see the structure, and explain the `mise`-on-top-of-`uv` layering.

- ❌ Bad: "What does `_PREFIX_RE` match?" → recall.
- ✅ Good: "Walk through why CSVs in `data/` are named with a `NN_` prefix. What would go wrong if you removed the prefix? Use a multi-table lesson as your example." → forces a tour of `csv_to_sqlite.py:27`, the FK-ordering invariant, and a concrete lesson like `14-inner-join/data/`.

- ❌ Bad: "How many lessons are there?" → trivia.
- ✅ Good: "Why is the curriculum 22 lessons (not 5, not 50), and why is it shaped as 'one new industry per lesson'? What would be lost by reusing one big dataset across all lessons?" → forces engagement with pedagogy.

## Setup & toolchain

- **Q-001** [tag: runbook, difficulty: easy]
  - **Q:** A new contributor cloned this repo and asks you what they need to type to get a working environment. Where would you point them, and what would you tell them about how the toolchain layers fit together?
  - **A:** Point them at `mise.toml` at the repo root — that one file declares both runtime versions (Python 3.12, uv, claude) and project tasks. The two commands they need are `mise run venv-create` (which runs `uv venv` to create `.venv/`) and `mise run inst` (which runs `uv sync --all-extras`). The reason this project layers `mise` on top of `uv` is that `mise` answers *both* "which Python version?" and "what commands do I run?", so a teammate doesn't have to memorize separate `pyenv` / `uv` / `make` stacks. `CLAUDE.md` documents the same commands for AI tooling, but `mise.toml` is the source of truth.

Python only matters if `db.sqlite` is corrupted (you'd run `gen_db.py` to rebuild it) or if you want to run the batch self-test (`python examples/check_examples.py`). - **Q-003** [tag: runbook, knowhow, difficulty: medium]

  - **A:** It walks every `examples/NN[-_]*/` folder, opens `db.sqlite` with SQLAlchemy, executes each `example_*.sql` file, and reports OK/ERR with the row count of the last result set (see `examples/check_examples.py:85-128`). ## CSV-to-SQLite loader

- **Q-005** [tag: knowhow, mech, difficulty: medium]
  - **Q:** Walk through what `learn_sql_query_basic/csv_to_sqlite.py` does end-to-end. Which steps could be done with `pandas` or `sqlite3` directly, and why does the project use `polars` + `SQLAlchemy` instead?
  - **A:** `load_csv_dir_to_sqlite(csv_dir, db_path)` at `csv_to_sqlite.py:60` deletes the target DB, creates a fresh SQLAlchemy engine, then for each CSV (in sorted-glob order, which gives FK-dependency order via the `NN_` prefix) it reads the CSV with `polars.read_csv`, maps polars dtypes to SQLAlchemy types via the switch at `:34`, builds a `Table` with `_build_table`, creates it, and bulk-inserts via `engine.begin()`. Pandas would work for reading; sqlite3 would work for writing. The actual reason for polars + SQLAlchemy is API ergonomics: polars's `df.schema[col]` returns a typed `DataType` that maps cleanly via a small if/elif switch, and SQLAlchemy's `Table(..., metadata, *columns)` is far more readable than building `CREATE TABLE` strings — the loader stays at 97 lines instead of 200.
  - **Source:** `learn_sql_query_basic/csv_to_sqlite.py`

- **Q-006** [tag: knowhow, convention, difficulty: medium]
  - **Q:** Why are CSV files in `data/` prefixed `NN_<name>.csv`? What would break if you renamed `examples/14-inner-join/data/02_visits.csv` to `visits.csv`, and why?
  - **A:** The `NN_` prefix exists so that `sorted(csv_dir.glob("*.csv"))` at `csv_to_sqlite.py:83` walks CSVs in foreign-key dependency order — `01_pets.csv` loads before `02_visits.csv` because visits reference pet_id values that must already exist in `pets`. The regex at `:27` (`r"^\d+_"`) strips the prefix from the **table name** so the resulting table is just `visits`. If you renamed it to `visits.csv`, the file would now sort alphabetically *before* `01_pets.csv` and the load order would flip. In this specific repo no actual `FOREIGN KEY` constraint is created (the loader builds plain dtype-inferred tables), so it would technically still load — but the convention is load-bearing for cross-engine portability and for learner expectations.
  - **Source:** `learn_sql_query_basic/csv_to_sqlite.py:27`, `csv_to_sqlite.py:83`

- **Q-007** [tag: knowhow, mech, difficulty: hard]
  - **Q:** `csv_to_sqlite.py` does `db_path.unlink()` unconditionally at line 77 before recreating the DB. Why? What's the principle, and when would this design choice burn you?
  - **A:** The unconditional delete enforces **full reproducibility**: every run of `gen_db.py` produces a DB identical to what's reconstructible from the CSV inputs, with zero accumulated state from a previous run. This matters because lesson DBs are committed to git — if a CSV was edited and the loader merged rows instead of replacing, the on-disk DB would silently drift from the CSV (the source of truth). The choice burns you if you accidentally pass the wrong `db_path` — the loader will happily delete whatever file is there. Mitigation in this codebase: every lesson's `gen_db.py` hardcodes `DB_PATH = HERE / "db.sqlite"` so the path is always a known sibling of the script.
  - **Source:** `learn_sql_query_basic/csv_to_sqlite.py:73-80`

- **Q-008** [tag: knowhow, mech, difficulty: hard]
  - **Q:** The loader infers SQLAlchemy column types from polars dtypes (`polars_dtype_to_sqlalchemy`, `csv_to_sqlite.py:34`). Walk through what happens to a column that polars infers as `Utf8` (string) but the data actually looks like dates (e.g. `"2025-05-12"`). What's the implication for the SQL learners then write?
  - **A:** The fallthrough at `:45` returns `sa.Text()`, so a date-looking column becomes a `TEXT` column in SQLite. SQLite has no native `DATE` type anyway (it stores ISO-8601 strings as TEXT), so this is fine for SQLite. The learner-facing consequence shows up in lesson 10 (built-in functions): `date()` and `strftime()` happily operate on ISO-8601 text strings — that's how SQLite was designed. But if the course were ported to Postgres, the same data would need to be cast (`CAST(col AS DATE)`) or the loader would need to call `pl.read_csv(..., try_parse_dates=True)`. The current design is a coupled-to-SQLite simplification.
  - **Source:** `learn_sql_query_basic/csv_to_sqlite.py:34-45`, `examples/10-builtin-functions/`

## check_examples.py harness

- **Q-009** [tag: mech, knowhow, difficulty: medium]
  - **Q:** `check_examples.py:57` tries to execute the whole SQL file as a single statement first, and only falls back to splitting on `;` if that fails. Why this order? What's the alternative design and why is the chosen one better?
  - **A:** A single SQL file in this course usually contains one statement, sometimes more. The naive "always split on `;`" design would break on files like `examples/12-group-by/example_06.sql` whose comment block at lines 24-30 contains a deliberately-broken example SQL ending in `;` — splitting would treat that comment-SQL as a real statement. By trying the whole file first and only splitting on failure, the harness handles 99% of files cleanly and falls back gracefully on the rare multi-statement case (lines 68-82). The alternative — always strip comments then split — works too but requires a more elaborate comment stripper to handle nested `/* */`. The chosen design is "lazy parsing": let SQLAlchemy decide, fall back only when needed.
  - **Source:** `examples/check_examples.py:57-82`, `examples/12-group-by/example_06.sql:24-30`

- **Q-010** [tag: convention, knowhow, difficulty: medium]
  - **Q:** Why does `LESSON_RE` at `check_examples.py:28` accept `^\d{2}[-_].+` (both hyphen and underscore)? What does this character-class hint at about the course's history?
  - **A:** Lesson 01's folder is `01-sharpen-your-tools` (underscore separator) while lessons 02-23 are `02-select-basics`, `03-select-columns-and-aliases`, etc. (hyphen). The harness's regex tolerates both because lesson 01 predates the hyphen convention and was never renamed. This is a small but instructive bit of history: rather than renaming the folder (which would break any external bookmark/URL pointing at lesson 01), the author tolerated the inconsistency in code. The principle is "prefer compatibility over consistency when consistency is cosmetic" — a senior-engineer instinct.
  - **Source:** `examples/check_examples.py:28`, `examples/01-sharpen-your-tools/`

## Lesson folder convention

- **Q-011** [tag: convention, pedagogy, difficulty: medium]
  - **Q:** Open `examples/12-group-by/` and `examples/20-cte-with/`. What's identical between them, and why is the uniformity load-bearing for learners?
  - **A:** Both folders contain `README.md` + `README-cn.md`, a `data/` subfolder with one or more `NN_<table>.csv` files, a committed `db.sqlite`, a `gen_db.py` that's nearly byte-identical between the two (5 lines of glue around `load_csv_dir_to_sqlite`), and a sequence of `example_NN.sql` files. The uniformity matters because once a learner has done lesson 02 they know exactly where to look in every subsequent lesson — README sets the business context, `data/` shows the schema, examples teach SQL one beat at a time. If lesson 20 had a different file layout, the learner would burn cognitive load on navigation instead of CTEs. The convention is the curriculum's UX.
  - **Source:** `examples/12-group-by/`, `examples/20-cte-with/`, `docs/learn-this-project/01-knowhow-inventory.md#lesson-folder-template-lessons-0223`

- **Q-012** [tag: pedagogy, knowhow, difficulty: medium]
  - **Q:** Open three random `example_*.sql` files from different lessons. What's the comment structure they share, and why does the course insist on it?
  - **A:** Every file opens with a `-- Business question:` block ("which category keeps the register busiest?", "for every clinic visit, show which pet came in") followed by a `-- Why this query:` block (the principle the SQL embodies — `GROUP BY` collapses rows, `INNER JOIN` stitches tables on a shared key). - **Q-013** [tag: pedagogy, knowhow, difficulty: hard]
  - **Q:** `examples/12-group-by/example_06.sql` is structurally different from the others — it shows a *broken* query in the comments before the corrected one. Walk through why this file exists in this shape, and what the lesson is about beyond just "GROUP BY".
  - **A:** Example 06 in lesson 12 teaches the "must appear in GROUP BY or be aggregated" rule — the classic GROUP BY footgun. The file shows the broken SQL (`SELECT cashier, item, SUM(...) FROM sales GROUP BY cashier`) inside a comment block (lines 24-30) so the learner can recognize the smell, then shows the fixed version below (lines 36-41). Critically, the comment also notes that **SQLite is lenient and would silently return a result** — "you get a result that looks fine but is meaningless" (lines 19-22). The pedagogical move is: "you'll write this bug; here's what it looks like; here's the engine behavior that lets it slip past you". This is the only example in the course shaped this way — most other lessons demonstrate working SQL; lesson 12.06 demonstrates a trap.
  - **Source:** `examples/12-group-by/example_06.sql`, `docs/learn-this-project/01-knowhow-inventory.md`

## Curriculum design

- **Q-014** [tag: pedagogy, knowhow, difficulty: medium]
  - **Q:** Why does each lesson use a different industry (books, drinks, gym, hotel, cinema, streaming, podcast, delivery, library, bank, conv. store, fitness, vet, ride-share, concert, retail, dating, subscription, real estate, coffee, soccer, weather)? What would the course lose by using one big dataset throughout?
  - **A:** A learner who sees `sales` 22 times stops thinking and starts pattern-matching. Each new industry forces them to **re-encode the business question** every lesson — "which `category` is busiest" becomes "which `cashier` rang the most" becomes "which `pet` came in most". That re-encoding work is the actual learning; the SQL is just the vocabulary. A single dataset would give the illusion of progress (the learner gets faster, the SQL grammar gets more complex) while the underlying skill — translating English business questions into SQL — never gets exercised. The cost of the design is curricular work: the author has to invent 22 distinct schemas and seed them realistically.
  - **Source:** `examples/README.md:22-130`, `docs/learn-this-project/01-knowhow-inventory.md#the-22-lesson-curriculum-lessons-0223`

- **Q-015** [tag: pedagogy, knowhow, difficulty: medium]
  - **Q:** Walk through the curriculum order. Why is window functions the **last** topic (lessons 22-23) and not earlier? Why is GROUP BY (lesson 12) before joins (lesson 14)?
  - **A:** The curriculum follows conceptual dependencies, not surface complexity. Window functions sit last because they require comfort with both `PARTITION BY` (a sibling of `GROUP BY`, taught in lesson 12) and `ORDER BY` inside a window (taught in lesson 07) — they're a composition of two earlier ideas. GROUP BY comes before joins because joins compose with grouping (you almost always GROUP BY after a JOIN in real reporting), but you can teach GROUP BY without ever joining. Doing joins first would mean lesson 14's queries either avoid aggregation entirely or sneak GROUP BY in untaught. The order is "single-table mechanics → grouping → joins → composition (subqueries/CTEs) → set algebra → windowing" — each topic only depends on what came before.
  - **Source:** `examples/README.md:22-130`, `docs/learn-this-project/01-knowhow-inventory.md`

- **Q-016** [tag: pedagogy, knowhow, difficulty: hard]
  - **Q:** The project tagline says "the course covers `SELECT` only — no clever tricks or advanced techniques". What does this constraint *cost* the course, and what does it *buy*? Where would you push back on the choice, and where would you defend it?
  - **A:** It costs depth: a graduate of this course can read window functions but cannot design a schema, has never written `CREATE TABLE` outside of lesson 01's setup, has no `EXPLAIN` literacy, doesn't know about indexes, and has never thought about transactions. It buys focus: a beginner who tries to learn schema design + SELECT simultaneously typically learns neither. The push-back is that "SELECT-only" makes the course incomplete for working backend engineers — they'll still need to learn the writeside elsewhere. The defense is that the analyst / data-scientist audience this course implicitly targets uses SELECT 90% of the time and benefits from a tight scope. The bigger risk is that learners may not know which 10% they're missing.
  - **Source:** `README.md`, `examples/README.md:1`, `docs/learn-this-project/03-elevation-roadmap.md#f-pedagogical-depth--beyond-syntax`

- **Q-017** [tag: pedagogy, knowhow, difficulty: medium]
  - **Q:** Lesson 01 (`01-sharpen-your-tools/`) is structurally different from every other lesson — different DB filename, different loader, different folder naming, no `example_*.sql` files. Why does this lesson exist, and why is it OK that it doesn't match the template?
  - **A:** Lesson 01 teaches DBeaver — how to download it, connect to a SQLite file, browse tables, run a query. It deliberately has no SQL exercises because the goal is environment readiness, not SQL skill. The forum schema (`users` / `posts` / `replies`) is small and conceptually familiar so the learner spends zero brain on the data and all of it on the tool. Using raw `sqlite3` with `executescript()` for the seed (`build_db.py`) instead of polars+SQLAlchemy is intentional too — the lesson wants to show CREATE TABLE + INSERT statements as proper SQL, which the CSV-based shared loader would hide. The differing template is the **right** signal: "this lesson is about something else; everything from lesson 02 onward is a uniform sequence."
  - **Source:** `examples/01-sharpen-your-tools/README.md`, `examples/01-sharpen-your-tools/build_db.py`, `docs/learn-this-project/01-knowhow-inventory.md#lesson-01--bootstrap-different-shape-from-0223`

## SQL teaching specifics (cross-lesson)

- **Q-018** [tag: series, knowhow, difficulty: medium]
  - **Q:** Lesson 04 deliberately introduces a `= NULL` "trap" that lesson 06 then fixes with `IS NULL`. Walk through why the course chooses to **show the broken pattern first**. What does the learner gain compared to teaching `IS NULL` upfront?
  - **A:** The course's pedagogical bet is that **learners remember what they got wrong** better than what they were told. By writing `WHERE col = NULL` in lesson 04 and seeing 0 rows come back, the learner forms a "what just happened" pause that lesson 06 then resolves — `IS NULL` is now the answer to a question they actually have, not a piece of trivia to memorize. The cost is dishonesty for two lessons (the learner is briefly walking around with a misconception) and risk of failure (a learner who stops mid-course is left with a bug). The course mitigates the second by pre-announcing in lesson 04's README that lesson 06 will fix it.
  - **Source:** `examples/README.md:35`, `examples/README.md:45`, `examples/04-where-basics/README.md`, `examples/06-where-like-in-between-null/README.md`

- **Q-019** [tag: series, knowhow, difficulty: hard]
  - **Q:** Lesson 18 teaches `IN (subquery)` and warns about the `NOT IN` + NULL trap; the same lesson then introduces `EXISTS` / `NOT EXISTS` as the "NULL-safe alternative". Why are these two ideas taught **together in the same lesson** rather than separately?
  - **A:** The two patterns answer the same business question ("which rows have a match in another set?") but with different NULL semantics — `WHERE id NOT IN (SELECT id FROM t)` returns 0 rows if `t.id` contains any NULL, while `WHERE NOT EXISTS (...)` doesn't. If a learner is taught `IN`/`NOT IN` first as a complete lesson and `EXISTS`/`NOT EXISTS` a week later, they'll happily use `NOT IN` in production and hit the NULL trap. Pairing them in one lesson makes the comparison vivid — the learner sees the bug and the fix in the same sitting, and walks away with `EXISTS` as the muscle memory rather than `IN` plus a warning they'll forget.
  - **Source:** `examples/README.md:103-106`, `examples/18-subqueries-in-where/`

- **Q-020** [tag: series, knowhow, difficulty: hard]
  - **Q:** Lessons 19 (subqueries in SELECT/FROM) and 20 (CTEs) cover overlapping ground — both let you compose queries from sub-results. Walk through why the course teaches them as separate lessons in this order, and where one is preferred over the other.
  - **A:** Lesson 19 shows scalar subqueries in `SELECT` (one value per row), derived tables in `FROM` (a one-shot inline view), and correlated subqueries (a per-row lookup). Lesson 20 reframes the same composition with `WITH name AS (...)` — same expressiveness, but **named** intermediate results. The course teaches subqueries first because they're closer to the SQL grammar a learner has already seen (lesson 18) and the syntactic "lift" of CTEs is small once subqueries feel natural. Preference: use CTEs when there are 2+ intermediate steps, or when you want to name an idea ("active_users", "recent_orders"); use subqueries inline when it's one step and naming would add noise. Lesson 20's example 03 is exactly this — refactoring a nested subquery from lesson 19's style into chained CTEs.
  - **Source:** `examples/19-scalar-and-derived-subqueries/`, `examples/20-cte-with/`, `examples/README.md:107-115`

- **Q-021** [tag: series, knowhow, difficulty: medium]
  - **Q:** Lessons 14, 15, 16, and 17 are four consecutive JOIN lessons. Why does the course separate them instead of teaching joins in one big lesson? What does each lesson contribute that the previous one didn't?
  - **A:** Joins are not one idea; they're a family. Lesson 14 (INNER JOIN) introduces the basic shape — `ON` clauses, table aliases, qualified columns — using a 2-table scenario where every row matches. Lesson 15 (LEFT JOIN) introduces *asymmetry* — keeping left rows that have no right match, and the `IS NULL` anti-join idiom. Lesson 16 (multi-table) introduces *chaining* and mixing INNER+LEFT across 3–4 tables. Lesson 17 (self-join) introduces *the same-table-twice* mental trick, which is alien on first contact. Teaching them together would conflate "join syntax" with "join shape" with "join composition" — the learner would memorize a megaclass of patterns without internalizing the principle behind each. The 4-lesson sequence forces them to use each pattern with a clean dataset before piling on.
  - **Source:** `examples/14-inner-join/`, `examples/15-left-join/`, `examples/16-multi-table-joins/`, `examples/17-self-join/`

- **Q-022** [tag: series, knowhow, difficulty: medium]
  - **Q:** Lessons 22 and 23 are both window functions. Why split into two lessons rather than one big window-functions lesson?
  - **A:** Lesson 22 teaches **ranking** functions (`ROW_NUMBER`, `RANK`, `DENSE_RANK`) — these are conceptually closest to a "running counter" and don't require thinking about frames at all (you only need `PARTITION BY` and `ORDER BY`). Lesson 23 teaches **aggregate-as-window** + `LAG`/`LEAD` — these require understanding *frame clauses* (`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`) which is a denser conceptual hurdle. Bundling them would mean introducing partitioning, ordering, frames, ranking semantics, aggregation semantics, and LAG/LEAD in one sitting. Splitting lets lesson 22 establish the OVER clause's "partition + order" half before lesson 23 adds the "frame" half. Order matters: ranking before aggregates because ranking is a special case.
  - **Source:** `examples/22-window-functions-ranking/`, `examples/23-window-functions-aggregates/`, `examples/README.md:122-130`

## Conventions and design choices

- **Q-023** [tag: convention, knowhow, difficulty: medium]
  - **Q:** Every lesson folder ships **both** `README.md` and `README-cn.md`. What does the project gain from the bilingual setup, and what's the maintenance cost? When (if ever) would you drop one?
  - **A:** The bilingual setup widens the course's audience to Mandarin-speaking learners — a substantial population for whom SQL tutorials in fluent Chinese are scarce. The maintenance cost is real: every lesson edit must be mirrored in two files, and translation drift is a constant risk (an English clarification can land without a Chinese counterpart). You'd drop the Chinese version if (a) the author wants to publish the course as a portfolio piece in English and bilingual content reads as "translated"; (b) the audience shifts to English-primary; or (c) lesson edits stop being kept in sync (worse than no translation). The publish skill's checklist explicitly treats every `README-cn.md` as a cardinal-delete because a publish-bound portfolio has a different audience than a teaching repo.
  - **Source:** `examples/README.md`, `examples/README-cn.md`, `docs/learn-this-project/07-publish-checklist.md`

- **Q-024** [tag: convention, knowhow, difficulty: medium]
  - **Q:** Every lesson's `db.sqlite` is committed to git, even though `gen_db.py` can rebuild it deterministically from CSVs. Is this a smell or a choice? Walk through the tradeoff.
  - **A:** It's a deliberate choice that trades git-repo size for learner friction reduction. The alternative (CSV-only, no committed `.sqlite`) would force every learner to run `gen_db.py` before they can do anything, requiring a working Python environment as a precondition to *opening DBeaver*. By committing the DBs, the author makes the **first SQL query** the friction point instead of `pip install`. The cost: every `gen_db.py` re-run that updates a CSV will also update the binary `.sqlite`, which git-diffs poorly. Mitigation: the DBs are small (largest is ~200 rows × ~10 cols), so the bloat is bounded. The principle is "make the happy path frictionless, even if it makes git messier" — a teaching-product instinct.
  - **Source:** `examples/12-group-by/db.sqlite`, `examples/12-group-by/gen_db.py`, `examples/README.md:9`

- **Q-025** [tag: deps, knowhow, difficulty: medium]
  - **Q:** `pyproject.toml` pins `polars >=1.40.1,<2.0.0` and `SQLAlchemy >=2.0.33,<2.1.0`. What's the principle behind each pin, and what would change if both upper bounds were removed?
  - **A:** Both pins use the "minor-version-cap" convention: a major or minor bump can introduce breaking changes, so the bound says "I've tested with this band; an automated update past it could break me." For polars, the `<2.0.0` cap protects against polars 2.0's planned breaking changes (the read_csv API and dtype names are stable in 1.x). For SQLAlchemy, the `<2.1.0` cap is more conservative — minor versions of SQLAlchemy 2.x are largely additive, but Core APIs the loader uses (`Table`, `MetaData`, `engine.begin()`) are stable, so a future 2.1 would *probably* work. Removing the caps means a `uv sync` 18 months from now could install a version the loader doesn't handle and quietly break for the next learner who clones.
  - **Source:** `pyproject.toml:5-8`, `learn_sql_query_basic/csv_to_sqlite.py`

- **Q-026** [tag: deps, knowhow, difficulty: medium]
  - **Q:** Why does `csv_to_sqlite.py` use SQLAlchemy **Core** (the `Table`/`MetaData`/`Column` API) rather than ORM (declarative models)? What changes if you tried to swap in ORM?
  - **A:** ORM requires a class definition per table written ahead of time: `class Books(Base): id = Column(Integer, primary_key=True); ...`. But this loader builds tables **at runtime** from CSV dtypes — there's no fixed schema known in advance. Using ORM would mean generating model classes dynamically (with `type(...)` or similar metaprogramming), which is heavier code and worse error messages. Core's `Table(name, metadata, *columns)` constructor is exactly the right level: programmatic schema, automatic dtype-to-column mapping (`csv_to_sqlite.py:34`), bulk insert via `table.insert()`. ORM also adds session management, identity maps, and lazy loading — all overhead for a one-shot loader. The principle: "use the lightest layer of the dep that does the job."
  - **Source:** `learn_sql_query_basic/csv_to_sqlite.py:48-57`, `learn_sql_query_basic/csv_to_sqlite.py:60-96`

- **Q-027** [tag: convention, knowhow, difficulty: hard]
  - **Q:** `_build_table` in `csv_to_sqlite.py` creates columns with **no primary keys, no FK constraints, no indexes, no NOT NULL**. Lesson 14 has `pets` + `visits` with a clean FK relationship — and yet the loaded tables don't enforce it. Walk through why this isn't a bug, and where the FK relationship actually lives.
  - **A:** The loader's job is to load *the CSV contents* into SQLite — it does not own schema design. In this course, the FK relationship between `visits.pet_id` and `pets.pet_id` lives in the CSV data (every `visits.pet_id` is a real `pets.pet_id`) and in the lesson README's schema diagram, not in the engine constraints. The reason this works: CSVs are hand-curated for teaching, so referential integrity is guaranteed by construction. Adding `ForeignKey` declarations would (a) require the loader to know which column references which — extra config — and (b) only matter if the data were dirty. The principle: "enforce in the source of truth, not at every layer." The cost: a learner cannot rely on the loaded DB to teach them about FK constraint violations — which is fine because the course is SELECT-only.
  - **Source:** `learn_sql_query_basic/csv_to_sqlite.py:48-57`, `examples/14-inner-join/data/`

- **Q-028** [tag: knowhow, mech, difficulty: hard]
  - **Q:** Lesson 01's `build_db.py` uses raw `sqlite3.executescript(...)` instead of the shared `csv_to_sqlite.load_csv_dir_to_sqlite`. Walk through both designs side by side — what does each get the lesson, and why is the inconsistency a feature?
  - **A:** Lessons 02-23 need data **already in SQLite** so the learner can immediately run SELECTs against rich schemas; the CSV-based loader makes that fast to author. Lesson 01 is about teaching DBeaver — its purpose is to **show the learner what a CREATE TABLE + INSERT looks like as raw SQL** because they'll see those statements in any database course they take after. Using the shared CSV loader for lesson 01 would hide the CREATE TABLE statements behind polars/SQLAlchemy abstractions — exactly what the lesson doesn't want. So `build_db.py` does `executescript(open("sql/01_schema.sql").read())` then `executescript(open("sql/02_seed.sql").read())`, and the SQL files are committed for the learner to read. The inconsistency between lesson 01 and 02+ isn't sloppiness — it's that lesson 01 has a different teaching goal.
  - **Source:** `examples/01-sharpen-your-tools/build_db.py`, `examples/01-sharpen-your-tools/sql/01_schema.sql`, `examples/01-sharpen-your-tools/sql/02_seed.sql`

## Reflection and meta

- **Q-029** [tag: pedagogy, knowhow, difficulty: hard]
  - **Q:** Suppose a learner has finished all 22 SQL lessons (02-23). What **can** they now do, and what would still trip them up in a junior data-analyst interview?
  - **A:** They can read and write basic-to-intermediate `SELECT` queries: filtering, grouping, joins of all major shapes, subqueries, CTEs, set operations, ranking and aggregate window functions. They can translate "show me X by Y" business questions into SQL. They will be tripped up by: schema design (the course never asks them to design one); index reasoning and `EXPLAIN` reading (not taught); writes (INSERT/UPDATE/DELETE); transactions and isolation; date arithmetic at scale; recursive CTEs; `LATERAL`/`CROSS APPLY`; performance under realistic data volumes; dialect-specific differences (the course is SQLite-only); ETL design. A self-aware graduate would describe themselves as "comfortable writing SELECT queries against a well-shaped schema" — which is accurate and useful.
  - **Source:** `examples/README.md`, `docs/learn-this-project/03-elevation-roadmap.md#f-pedagogical-depth--beyond-syntax`

- **Q-030** [tag: pedagogy, knowhow, difficulty: hard]
  - **Q:** The course has zero exercises — every `example_*.sql` shows the answer. Walk through why this might be a deliberate pedagogical choice, and where it stops working.
  - **A:** The choice is "show, don't test": every example is a worked solution with the business question and the rationale baked in. The bet is that a beginner who reads 100+ worked SQLs deeply internalizes shape and idiom better than one who attempts 100+ exercises and gets stuck. It works for the "I want to learn how to read SQL and write small variations" path. It stops working for "I want to prove I can produce SQL under exam conditions" — the learner has never had to write SQL from a blank file, so their first real attempt is in front of a real problem. The elevation roadmap (`docs/learn-this-project/03-elevation-roadmap.md#d-exercises-your-turn-mode`) flags this gap as a 3-6 month upgrade direction: add a parallel `exercises/` folder per lesson with prompts whose answers the learner writes themselves.
  - **Source:** `examples/12-group-by/example_01.sql`, `docs/learn-this-project/03-elevation-roadmap.md#d-exercises-your-turn-mode`

- **Q-031** [tag: pedagogy, knowhow, difficulty: medium]
  - **Q:** If you were inheriting this course tomorrow and could only do **one** improvement before publishing, what would it be — and what's your reasoning for that choice over the alternatives?
  - **A:** Add CI + result-snapshot tests (`docs/learn-this-project/03-elevation-roadmap.md#a-test-depth-and-coverage` + `#b-ci--cd-maturity`). Reason: the course's biggest hidden risk is that an edit to a CSV or SQL silently breaks a lesson and ships to learners that way. The current `check_examples.py` only catches parse errors, not wrong answers. With snapshot tests + GitHub Actions, every edit is verified end-to-end against the committed expected results, and the green checkmark is the publish-quality signal. Alternatives I'd defer: exercises (high-value but high-build; ~2 weeks); cross-engine (high-value but optional for the SQLite-target audience); static site (polish, not substance). CI is the cheapest high-leverage move and unblocks everything else.
  - **Source:** `docs/learn-this-project/03-elevation-roadmap.md`, `examples/check_examples.py`
