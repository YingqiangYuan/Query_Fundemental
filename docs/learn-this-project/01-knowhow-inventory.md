# Know-how Inventory — `learn_sql_query_basic`

> Scope note (from meta-skill bootstrap): analysis is tightly scoped to the lesson series under `examples/` plus the toolchain (`learn_sql_query_basic/csv_to_sqlite.py`, `pyproject.toml`, `mise.toml`). Hypothetical features outside this surface are not speculated about.

## Project at a glance

`learn_sql_query_basic` is a hands-on, SELECT-only SQL course. It is delivered as **23 self-contained lesson folders** under `examples/` — one bootstrap lesson on DBeaver (`01_sharpen_your_tools/`) plus 22 query lessons (`02-select-basics/` … `23-window-functions-aggregates/`). Each lesson ships its own real-world dataset, a pre-generated `db.sqlite` (committed to git), and a handful of `example_NN.sql` files whose top-of-file comments explain **the business question** and **why the query is written that way**. The audience is beginners who already know what a table is but want to grow from "I can write `SELECT *`" to "I can read window functions". The project explicitly avoids INSERT/UPDATE/DELETE/DDL so learners can focus on query logic without worrying about mutation.

## Architecture overview

```
learn_sql_query_basic-project/
├── learn_sql_query_basic/          ← shared Python helper package (one module)
│   └── csv_to_sqlite.py            ← polars → SQLAlchemy → SQLite loader
├── examples/                       ← the entire teaching surface
│   ├── README.md / README-cn.md    ← course index (bilingual)
│   ├── check_examples.py           ← batch self-test harness
│   ├── 01_sharpen_your_tools/      ← DBeaver bootstrap lesson (unique shape)
│   └── NN-<topic>/  (×22)          ← uniform lesson folders, lessons 02-23
│       ├── README.md / README-cn.md
│       ├── data/NN_<table>.csv     ← seed CSVs, FK-ordered by NN_ prefix
│       ├── db.sqlite               ← pre-generated, committed to git
│       ├── gen_db.py               ← rebuild db.sqlite from CSVs
│       └── example_0N.sql          ← teaching SQL with header comments
├── mise.toml                       ← Python 3.12 + uv + project tasks
└── pyproject.toml                  ← deps: polars + SQLAlchemy 2.x
```

There is one execution model: **a learner opens `db.sqlite` in DBeaver (or `sqlite3`) and runs the SQL files one at a time**. There is no server, no service, no UI. The Python code only exists to (a) build the SQLite files from CSVs and (b) batch-verify every committed SQL still runs.

## Component inventory

### Shared helper package

#### `learn_sql_query_basic/csv_to_sqlite.py`

- **What.** A single-purpose loader that recreates a SQLite file from every CSV in a directory. Reads CSVs with polars, infers dtypes, builds SQLAlchemy `Table` objects, and bulk-inserts rows in one transaction per table.
- **Why.** Every lesson needs a fresh, reproducible `db.sqlite`. Centralizing the CSV→SQLite step in one helper means each lesson's `gen_db.py` is reduced to 5 lines of glue — no duplicated loading logic, no opportunity for lessons to drift apart on dtype handling.
- **Key files.** `learn_sql_query_basic/csv_to_sqlite.py:30` (`csv_path_to_table_name`), `:34` (`polars_dtype_to_sqlalchemy`), `:60` (`load_csv_dir_to_sqlite`).
- **Depends on.** `polars`, `sqlalchemy`.
- **Gotchas.**
  - CSV filenames must be `NN_<table>.csv` (e.g. `01_users.csv`). The `NN_` prefix controls load order so parent tables populate before child tables that reference them; the regex at `:27` strips the prefix to derive the table name. A CSV without the prefix would load in alphabetical order — fine for a single-table lesson, dangerous for multi-table lessons that rely on FK ordering.
  - `db_path.unlink()` is called unconditionally at `:77` — the destination file is **always deleted first**. That is by design (reproducibility) but it means accidentally pointing `gen_db.py` at the wrong file deletes it.
  - There are **no actual `FOREIGN KEY` constraints** built. Tables are dtype-inferred plain tables; the FK relationships only exist in the learner's mental model (and the lesson READMEs). The `NN_` prefix is purely a load-order convention.
  - `_build_table` (`:48`) creates columns with inferred types but **no primary keys, no indexes, no constraints**. Lessons that need FKs (e.g. 14-inner-join) work because the data is clean, not because the schema enforces anything.

#### `learn_sql_query_basic/__init__.py`

- **What.** Re-exports `csv_path_to_table_name`, `load_csv_dir_to_sqlite`, `polars_dtype_to_sqlalchemy`.
- **Why.** Gives every per-lesson `gen_db.py` a stable top-level import (`from learn_sql_query_basic import load_csv_dir_to_sqlite`).
- **Gotchas.** None.

### Lesson harness

#### `examples/check_examples.py`

- **What.** Walks every `examples/NN[-_]*` folder, opens its `db.sqlite`, runs every `example_*.sql` file via SQLAlchemy, prints `OK`/`ERR` + row count per file, exits non-zero if any SQL erred.
- **Why.** This is the project's only test. When a lesson is edited (CSV changed, schema tweaked, SQL rewritten) it's the one command that confirms every committed SQL still parses and returns rows against every committed `db.sqlite`. Without it, the bilingual READMEs and per-lesson DBs would drift undetected.
- **Key files.** `examples/check_examples.py:42` (`split_statements` — strips comments before splitting on `;`), `:57` (`run_sql_file` — fast-path single statement, fallback multi-statement), `:85` (`main`).
- **Depends on.** `sqlalchemy`, stdlib `re`.
- **Gotchas.**
  - Tries the whole file as one statement first; only falls back to splitting on `;` if that fails. This is because comments may legitimately contain semicolons (e.g. lesson 12's `example_06.sql` shows a broken-SQL example inside a `--` block).
  - Reports only the **last** row-returning statement's row count for multi-statement files; intermediate counts are dropped.
  - `LESSON_RE = re.compile(r"^\d{2}[-_].+")` at `:28` accepts both `01_sharpen_your_tools` (underscore) and `02-select-basics` (hyphen). This is deliberate — lesson 01 was named first and uses underscores; everything 02+ uses hyphens. The regex bridges the inconsistency.
  - `WHY: <best guess; verify with project owner>` for why lesson 01 is named differently — likely an early naming convention that was changed before lesson 02 but never retro-applied to 01.

### Course index

#### `examples/README.md` and `examples/README-cn.md`

- **What.** The top-level lesson index — links every lesson folder with a one-line goal, dataset, and "you'll learn" bullet.
- **Why.** Gives a learner who lands in `examples/` (without reading the repo root) a map of the curriculum. The Chinese counterpart (`README-cn.md`) supports Mandarin-speaking learners; every lesson folder mirrors the same bilingual pattern.
- **Key files.** `examples/README.md:22` (lesson 02 starts here), `examples/README.md:131` (lesson 23 ends here).
- **Gotchas.**
  - The "How to use this tutorial" section explicitly tells learners that **`db.sqlite` is pre-generated and committed** — they should *not* run `gen_db.py` unless the file is corrupted. This is load-bearing context for understanding why the per-lesson `gen_db.py` files look like they're "unused".

### Lesson 01 — bootstrap (different shape from 02–23)

#### `examples/01_sharpen_your_tools/`

- **What.** A DBeaver installation + first-SQLite-connection tutorial. Ships a tiny forum schema (`users`, `posts`, `replies`; 8/12/30 rows) and walks through DBeaver download → connection → `SELECT * FROM posts LIMIT 5;`.
- **Why.** The course assumes a working SQL editor and a learner who can open a `.sqlite` file. Without this lesson, lessons 02+ have no entry point for someone who has never used DBeaver. The lesson is named with an underscore (`01_sharpen_your_tools`) where 02+ use hyphens (`02-select-basics`) — a historical naming inconsistency the harness tolerates via the `[-_]` regex character class.
- **Key files.** `examples/01_sharpen_your_tools/README.md` (180+ lines, 8 screenshots), `build_db.py` (uses raw `sqlite3.executescript`, not the shared loader), `sql/01_schema.sql`, `sql/02_seed.sql`, `imgs/use-dbeaver-0[1-8].png`.
- **Depends on.** stdlib `sqlite3` (notably **not** the shared `csv_to_sqlite` loader).
- **Gotchas.**
  - Uses raw `sqlite3` + `executescript` instead of polars+SQLAlchemy. **Why:** lesson 01 needs to seed via CREATE TABLE + INSERT statements (taught visually as proper SQL) rather than via CSV import. Using the shared CSV loader would hide the schema definitions the lesson is showing off.
  - The database file is named `forum.sqlite`, not `db.sqlite`. `check_examples.py` therefore skips lesson 01 (it looks specifically for `db.sqlite`). **WHY (best guess; verify with project owner):** lesson 01 has no `example_*.sql` files to verify, so excluding it from the harness is intentional, but the differing filename is the mechanism.

### Lesson folder template (lessons 02–23)

Every lesson folder under `examples/NN-<topic>/` follows the same uniform layout:

| File | Purpose |
| :--- | :--- |
| `README.md` | Bilingual-pair English version: business setup → "what we'll learn" table → "the data story" table → "open the database" instructions → "explore first" guidance → table of `example_NN.sql` → one teaching note (e.g. "SQL comment styles") |
| `README-cn.md` | Chinese translation of `README.md`, kept synchronized lesson-by-lesson |
| `data/NN_<table>.csv` | Seed CSV(s); the `NN_` prefix orders load so FK-parent tables load first |
| `db.sqlite` | Pre-generated SQLite file, committed to git — the learner's actual target |
| `gen_db.py` | 5-line wrapper around `load_csv_dir_to_sqlite(DATA_DIR, DB_PATH)` — used only when `db.sqlite` needs rebuilding |
| `example_01.sql` … `example_0N.sql` | Teaching SQL files. Each opens with a `--` block stating the **business question** ("Drinks, snacks, tobacco — which keeps the register busiest?") then a **why this query** block (the principle the SQL embodies), then 3–10 lines of actual SQL |

- **Why this uniform template.** Once a learner has done one lesson, every subsequent lesson is read with the same eye-path: README first (business + schema), then explore the data in DBeaver, then run examples one at a time. The uniformity is the curriculum's teaching pattern, not an accident.
- **Why each `example_NN.sql` has the business-question + why-this-query header.** The course is explicitly built around the principle 知其然知其所以然 (know what AND why). The SQL alone is the "what"; the comment block is the "why". A learner skimming just the SQL gets half the lesson.

### The 22-lesson curriculum (lessons 02–23)

The curriculum proceeds strictly in difficulty order. Each lesson uses a different industry context so learners don't burn out on one domain.

| # | Folder | Dataset | SQL focus |

| 04 | `04-where-basics/` | `gym_classes` (40) | comparison operators, the `= NULL` trap |

| 08 | `08-limit-offset-top-n/` | `chart_entries` (80) | `LIMIT`/`OFFSET`, top-N idiom |
| 09 | `09-computed-columns-and-case/` | `delivery_orders` (60) | arithmetic, `\|\|`, `CASE WHEN` |
| 10 | `10-builtin-functions/` | `checkouts` (50) | string/numeric/date functions, `COALESCE` |
| 11 | `11-aggregate-functions/` | `transactions` (100) | `COUNT/SUM/AVG/MIN/MAX`, `COUNT(DISTINCT)` |

- **Why this ordering.** Lessons 02–11 are single-table mechanics. Lessons 12–13 introduce grouping. Lessons 14–17 introduce joins (each new join shape one at a time). Lessons 18–20 introduce subqueries and CTEs (composition). Lesson 21 is set algebra. Lessons 22–23 are window functions — the last topic because they require comfort with `PARTITION BY` (a relative of `GROUP BY`) and `ORDER BY`.
- **Why each lesson uses a different industry.** A learner who sees `sales` 22 times stops thinking and starts pattern-matching. Switching domains (bookstore → café → gym → hotel → cinema → streaming → podcast → delivery → library → bank → conv. store → fitness → vet clinic → ride-share → concert ticketing → retail org chart → dating app → subscription box → real estate → coffee shop → soccer league → city weather) forces the learner to re-encode the business question every lesson — that's the work, not the SQL.

## Conventions

- **`NN_<table>.csv` prefix → FK load order.** Lesson 14 has `data/01_pets.csv` and `data/02_visits.csv` because visits reference pets. Lesson 20 has 3 CSVs in dependency order. Convention enforced by `_PREFIX_RE` in `csv_to_sqlite.py:27`.
- **Pre-generated `db.sqlite` committed to git.** Removes the "I have to set up Python before I can run SQL" tax — a learner can open DBeaver and the file is right there. `gen_db.py` is escape-hatch-only.
- **Bilingual READMEs.** Every lesson ships `README.md` + `README-cn.md`. Lock-step structure; the Chinese version is a translation, not a different lesson.
- **Header-comment teaching format.** Every `example_NN.sql` opens with `-- Business question:` then `-- Why this query:` then SQL. Example: `examples/12-group-by/example_01.sql:1-12`. Deviating breaks the course's teaching pattern.
- **SELECT-only.** No INSERT/UPDATE/DELETE/DDL anywhere in any `example_*.sql`. Stated in `README.md:3` ("no clever tricks or advanced techniques") and `examples/README.md:1` ("the course covers `SELECT` only").
- **Different industry per lesson.** No lesson reuses another's dataset. New folder, new domain, new mental model.
- **Lesson 01 is the only exception** — different filename (`forum.sqlite` not `db.sqlite`), different loader (raw `sqlite3` not the shared module), folder named with underscore not hyphen.

## External dependencies

- **`polars >=1.40.1, <2.0.0`** (pinned in `pyproject.toml:6`). Used only in `csv_to_sqlite.py` for CSV reading + dtype inference. **Why polars over pandas:** no explicit rationale in the repo. Best guess (verify with project owner): polars 1.x has clean schema inspection (`df.schema[col]` returns a typed `DataType`) which maps cleanly to the SQLAlchemy column-type switch at `csv_to_sqlite.py:34`, and the loader processes datasets of 10–200 rows where polars's performance edge over pandas is irrelevant — the win is API clarity, not speed.
- **`SQLAlchemy >=2.0.33, <2.1.0`** (pinned in `pyproject.toml:7`). Used in `csv_to_sqlite.py` for `Table`/`MetaData`/`Column` construction + `engine.begin()` bulk insert, and in `check_examples.py` for `sa.text()`-based statement execution. **Why Core, not ORM:** the loader needs to build tables from dtype-inferred schemas at runtime — no declarative model exists ahead of time. ORM would require generating model classes dynamically, which is more code and worse error messages. Core is the right level. **Why SQLAlchemy at all, not raw `sqlite3`:** for `check_examples.py`, SQLAlchemy gives transaction handling + cross-engine syntax should the course ever expand beyond SQLite. For `csv_to_sqlite.py`, `Table(...).create(engine)` is far more readable than building `CREATE TABLE` strings with f-strings.
- **`mise` (toolchain manager)** + **`uv` (Python package manager)**. Declared in `mise.toml`. **Why mise:** answers both "which Python version?" and "what commands do I run?" in one file, so a contributor doesn't need separate `pyenv` + `Makefile` + `requirements.txt` stacks. **Why uv:** fast, modern, no need to manage pip+venv manually.
