# Interview Playbook — `learn_sql_query_basic`

> Production-grade interviewer questions for an engineer who built this project. Probes reasoning and tradeoffs, not trivia. Model answers are reference for the interview skill to grade against — they are **not** to be shown to the candidate.

## Opening — the 90-second pitch (model script ~150 words)

> "It's a SELECT-only SQL course in 23 lessons. Lesson 01 is a DBeaver setup walkthrough; lessons 02 through 23 each cover one query construct — SELECT, WHERE, ORDER BY, joins, GROUP BY, CTEs, window functions — using a different industry per lesson so the learner has to re-encode the business question each time. Every lesson is a self-contained folder with a pre-generated SQLite database committed to git, so a learner can open it in DBeaver immediately without setting up Python. Under the hood there's a small Python helper that uses polars to read CSVs and SQLAlchemy Core to build the SQLite tables — that's the one shared module, ~100 lines. There's also a self-test harness that runs every committed SQL against its database to catch parse errors. The course is bilingual — English and Mandarin — and explicitly excludes INSERT/UPDATE/DELETE and schema design to keep the scope tight."

What to listen for: do they emphasize the **why** (per-lesson industry, committed DBs, SELECT-only scope) or only the **what**? If only the what, probe with "why?" in every round.

## Round 1 — what you have (architecture & mechanism)

### Q1.1 — Walk me through what happens from `git clone` to a learner running their first SQL query.

- **Model answer.** Clone the repo. The learner installs `mise` once, runs `mise install` (pins Python 3.12 and uv per `mise.toml`), then `mise run venv-create && mise run inst`. They open DBeaver, point it at `examples/02-select-basics/db.sqlite`, and run a SELECT — that file is already committed, so no Python ran between clone and SQL. The Python infrastructure (`gen_db.py`, `learn_sql_query_basic/csv_to_sqlite.py`) only matters if a DB needs rebuilding or `check_examples.py` is run.
- **Follow-ups.** "Why pre-commit the DBs? Why not regenerate on first run?" / "What does mise add that uv alone wouldn't?"
- **Weak answer.** Reads off `mise.toml` task names without explaining the pre-committed-DB design choice.

### Q1.2 — Walk me through `learn_sql_query_basic/csv_to_sqlite.py`. What does each function do, and why is the file shaped this way?

- **Model answer.** `csv_path_to_table_name` strips a `NN_` prefix (`r"^\d+_"`) so `01_users.csv` becomes table `users`. `polars_dtype_to_sqlalchemy` is a small switch from polars dtypes to SQLAlchemy column types — Integer/Float/Boolean/Date/DateTime/Text fallthrough. `_build_table` constructs a `sa.Table` from a polars DataFrame's schema. `load_csv_dir_to_sqlite` is the entry point: it unconditionally deletes the target DB, iterates over `sorted(csv_dir.glob("*.csv"))` (sorted gives FK-load order via the `NN_` prefix), and for each CSV reads with polars → builds Table → creates → bulk-inserts in one `engine.begin()` transaction. The shape is "minimum code that gives every lesson reproducible CSV→SQLite".
- **Follow-ups.** "Why polars over pandas?" / "Why unconditional unlink? What does that protect against?" / "What if a CSV has a column polars can't infer cleanly?"
- **Weak answer.** Lists the functions without explaining the FK-ordering invariant or the reproducibility-via-unlink design.

### Q1.3 — Walk me through `examples/check_examples.py`. What kind of regression would it catch, and what would it miss?

- **Model answer.** It walks every `examples/NN[-_]*` folder, opens `db.sqlite` via SQLAlchemy, executes each `example_*.sql` via `sa.text()`, and reports OK/ERR + row count. Multi-statement files: it tries the whole file as one statement first (fast path, because comments may contain semicolons — see `examples/12-group-by/example_06.sql`), and only falls back to comment-stripped `;`-splitting if that fails. **Catches:** SQL that doesn't parse, missing tables, typo'd column names. **Misses:** result correctness (a SQL that returns *wrong* rows still says OK), CSV→SQLite regeneration drift (doesn't run `gen_db.py`), cross-engine portability (SQLite only).
- **Follow-ups.** "How would you upgrade it to catch wrong-answer regressions?" / "Why doesn't it test against Postgres? Should it?"
- **Weak answer.** Describes it as "the test" without acknowledging it doesn't test correctness.

### Q1.4 — Walk me through one full lesson — pick lesson 12 (`12-group-by`). What's in the folder and why is it shaped that way?

- **Model answer.** README.md + README-cn.md (bilingual), `data/01_sales.csv` (120 rows of convenience-store receipts), `db.sqlite` (pre-generated), `gen_db.py` (5-line wrapper around the shared loader), and `example_01.sql` through `example_06.sql`. Each example file opens with `-- Business question:` then `-- Why this query:`, then SQL. Example 06 is unique — it shows a *broken* GROUP BY query (selecting a non-grouped, non-aggregated column) in a comment block, then the fixed version below. The shape is uniform across all 22 SQL lessons; the uniformity is the curriculum's UX so learners don't burn brain on navigation.
- **Follow-ups.** "Why six examples in this lesson and not three or ten?" / "Why include the broken version in example 06?"
- **Weak answer.** Describes the file names without explaining the header-comment convention or the broken-example design.

### Q1.5 — Lesson 01 has a different folder layout (underscore separator, `forum.sqlite` not `db.sqlite`, no `example_*.sql` files, uses raw `sqlite3` not the shared loader). Walk through why.

- **Model answer.** Lesson 01 teaches DBeaver — installing it, connecting to a SQLite file, browsing tables, running `SELECT * FROM posts LIMIT 5`. Its goal is environment readiness, not SQL skill. The seed is from `sql/01_schema.sql` + `sql/02_seed.sql` (CREATE TABLE + INSERT) using `sqlite3.executescript`, because the lesson **wants** the learner to see CREATE TABLE statements as raw SQL — using the CSV loader would hide them behind polars/SQLAlchemy. The folder name (`01_sharpen_your_tools` with underscore) predates the lesson 02+ hyphen convention; `check_examples.py:28` regex `r"^\d{2}[-_].+"` tolerates both. No `example_*.sql` files because there are no SQL exercises — the README has 8 screenshots walking through the DBeaver UI.
- **Follow-ups.** "If you were redesigning, would you unify the folder name? What would you lose?" / "Why not use the shared loader and still ship the SQL files for the learner to read?"
- **Weak answer.** "Lesson 01 is different" without identifying *why* (teaching tool, not SQL).

## Round 2 — what you'd elevate (drawn from 03-elevation-roadmap.md)

### Q2.1 — If you had 3 months, what would you change about how the course is tested?

- **Model answer.** Replace `check_examples.py`'s parse-only check with a `pytest` suite that snapshots expected result rows per SQL file. Use `syrupy` or `pytest-regressions`. The new suite catches wrong-answer regressions: an edit to a CSV that breaks lesson 12's expected output would fail loudly instead of silently passing. Layer GitHub Actions on top so every push runs the suite. The current `check_examples.py` becomes a smoke test that runs alongside.
- **Follow-ups.** "How do you handle row-order differences across SQLite versions?" / "Snapshots in git create big diffs on intentional edits — how do you keep that manageable?"
- **Weak answer.** "Add tests" without specifying snapshot-based correctness vs current parse-only.

### Q2.2 — The course is SQLite-only. When would you add Postgres?

- **Model answer.** When learners start asking "does this work in Postgres at work?" or when CI reveals dialect drift. Concretely: SQLite is lenient about the GROUP BY rule (see `examples/12-group-by/example_06.sql:14-22` — explicitly noted). Postgres is strict. Today the course documents this in prose; a Postgres CI lane would *enforce* it. Implementation: `testcontainers-python` to spin up Postgres in CI, reload each lesson's CSVs into it, re-run the SQL. Cheaper interim: add DuckDB (strict SQLite, no container needed) as a second engine.
- **Follow-ups.** "What's the maintenance overhead of supporting two engines? Where would lessons break?" / "What's the smallest first step — one lesson, one dialect-difference?"
- **Weak answer.** "Sure, add Postgres" without identifying the specific lessons that would diverge.

### Q2.3 — The course has zero exercises — every example shows the answer. Defend or push back.

- **Model answer.** Defense: the course bets that worked-example density beats exercise density for beginners — every file is a complete demonstration with business question + rationale + SQL, and reading 100+ of these internalizes idiom faster than failing 100 exercises. Push-back: a learner who finishes has never written SQL from a blank file; their first real attempt is in front of a real problem. Resolution: add a parallel `exercises/` folder per lesson with prompts and hidden goldens, plus a graded checker. Keep the worked examples as the primary path; exercises are an opt-in "your turn" extension.
- **Follow-ups.** "How do you grade SQL that's semantically equivalent but textually different?" / "Where do hidden goldens live so they're not in the repo?"
- **Weak answer.** "Just add exercises" without considering that the no-exercises stance is a deliberate pedagogical bet.

### Q2.4 — Pick one upgrade area from the elevation roadmap and converge to a concrete starter deliverable. What would you build in week 1?

- **Model answer.** Pick CI (§ B): create `.github/workflows/test.yml` that runs `jdx/mise-action@v2`, then `mise install && mise run inst`, then `python examples/check_examples.py`. Cache the `.venv` and the mise downloads. That's ~50 lines of YAML, 1 hour of work, and immediately publishes a green-check on every push. It's the minimum-viable CI deliverable that unblocks everything else (the snapshot-test suite, cross-engine, etc.) because all subsequent work plugs into the same workflow.
- **Follow-ups.** "Why CI before the snapshot-test suite?" / "What's the failure mode of a green CI that's only running the parse check?"
- **Weak answer.** Picks an upgrade but doesn't narrow to a concrete first deliverable with a file path.

## Round 3 — alternatives considered ("why not X?")

### Q3.1 — Why polars and not pandas?

- **Model answer.** Tradeoff: polars 1.x has clean schema inspection (`df.schema[col]` returns a typed `DataType` that maps to SQLAlchemy column types in 5 lines — see `csv_to_sqlite.py:34-45`). Pandas's dtype model is messier (`object` dtype, NaN-vs-None handling) and would need more defensive code in the dtype switch. Performance is irrelevant — datasets are 10–200 rows. The win is **API clarity**, not speed. Counter-tradeoff: polars is less ubiquitous; a contributor more familiar with pandas would pause. Acceptable cost because the helper module is 97 lines and a contributor doesn't need to extend it often.
- **Follow-ups.** "How big a dataset before pandas's ergonomics start to matter in the opposite direction?" / "Would you make the same choice for a production ETL?"
- **Weak answer.** "Polars is faster" — ignores that speed isn't the actual reason at this scale.

### Q3.2 — Why SQLAlchemy Core and not raw `sqlite3` or the SQLAlchemy ORM?

- **Model answer.** Raw `sqlite3` works but means building `CREATE TABLE` strings with f-strings (sql-injection-style typing, harder to read, no type safety). ORM requires declarative model classes ahead of time — but this loader builds tables from runtime-inferred CSV dtypes, so there's no fixed schema to declare. ORM would force dynamic class generation, which is meta-programming overhead for a one-shot loader. Core hits the sweet spot: programmatic `Table(name, metadata, *columns)` with auto-dtype mapping, and `engine.begin()` for transactional inserts.
- **Follow-ups.** "If you were also teaching ORMs in this course, would you switch?" / "What's the test that proves Core is enough? When would Core start to creak?"
- **Weak answer.** "ORM is heavy" — vague; doesn't engage with "schema not known at write time".

### Q3.3 — Why a self-contained `db.sqlite` per lesson committed to git, instead of a single shared DB or CSV-only?

- **Model answer.** Per-lesson committed DB removes the "I need Python before I can do SQL" friction. A learner with only DBeaver installed can open the file and immediately run queries. CSV-only would force every learner to install Python first — friction that bounces beginners. A single shared DB across lessons would entangle lessons (a CSV edit in lesson 12 could affect lesson 13's data assumptions) and would force per-lesson namespace prefixes on table names (`grp_sales`, `join_pets`) that would clutter the SQL the learner reads. Per-lesson DBs cost git size (binary, diff-unfriendly) but datasets are tiny.
- **Follow-ups.** "How would you handle DB rebuilds in CI without committing the .sqlite?" / "What if the course grows to 100 lessons — does the git bloat tradeoff still hold?"
- **Weak answer.** "Easier for learners" — doesn't engage with the single-shared-DB alternative.

### Q3.4 — Why bilingual (English + Chinese) READMEs? Why not just English?

- **Model answer.** Mandarin-speaking learners face a real shortage of in-depth SQL tutorials in their language; the bilingual setup widens the audience meaningfully for low marginal authoring cost (a few hours per lesson). The maintenance cost is real — every English edit must be mirrored in Chinese, and drift is a constant risk. The setup pays off only if the Chinese audience is reached; if the publish-bound version of the course targets only English readers, the Chinese files become friction (translation work for no audience) and the publish skill explicitly treats every `README-cn.md` as a cardinal-delete.
- **Follow-ups.** "How do you keep them synchronized — manual or tooled?" / "If you were starting over, would you do bilingual day one or English first then translate later?"
- **Weak answer.** "Reaches more people" — doesn't engage with the maintenance cost.

## Round 4 — problems hit ("when something went wrong")

### Q4.1 — A learner reports `python examples/check_examples.py` errors on `01_sharpen_your_tools` with "db.sqlite missing". You investigate. Walk me through what happened and how you'd fix it.

- **Model answer.** Lesson 01 ships `forum.sqlite`, not `db.sqlite` — it's a different lesson by design (DBeaver tutorial). The harness looks specifically for `db.sqlite` (`check_examples.py:92`). The error means either (a) the harness picked up lesson 01 because `LESSON_RE = r"^\d{2}[-_].+"` matches it, OR (b) the learner has only a partial clone. **The current behavior** of `check_examples.py:99-104` is to print `"db.sqlite missing -- skipping N file(s)"` and continue — so if it actually errored, lesson 01 must have grown an `example_*.sql` file or the harness changed. Real fix: either rename lesson 01's DB to `db.sqlite` (breaks the README screenshots), or have the harness explicitly skip lesson 01 by name, or make the harness check for `example_*.sql` files before complaining about a missing DB.
- **Follow-ups.** "Which fix would you pick, and why?" / "What's the upstream defect that lets this confusion exist?"
- **Weak answer.** "Rebuild it with `gen_db.py`" — wrong tool; lesson 01 has `build_db.py` and a different name convention.

### Q4.2 — A new contributor edits `examples/12-group-by/data/01_sales.csv` to add a row. The committed `db.sqlite` is now stale relative to the CSV. How would you catch this in CI?

- **Model answer.** Today, you wouldn't — `check_examples.py` runs the SQL against the *committed* `db.sqlite` (not a regenerated one), so a stale DB passes silently. The fix is a pre-test step in CI: for each lesson, run `gen_db.py` into a temp DB, then compare schemas and row counts to the committed `db.sqlite`. Mismatch ⇒ fail. Alternatively, **delete the committed DBs from git and regenerate on every CI run** (and per-clone) — but that re-introduces the Python-before-SQL friction for learners. A pragmatic compromise: commit the DBs but enforce a "regen-on-CI" parity check.
- **Follow-ups.** "How would you sequence the test commits to avoid the parity check failing on the same PR that updates the DB?" / "Is the stale-DB risk big enough to justify the CI complexity?"
- **Weak answer.** "Add `pytest`" — doesn't identify the *specific* gap (committed DB vs CSV drift).

### Q4.3 — The harness reports `OK 5 rows` for `example_03.sql` in some lesson, but the learner says the README example output shows 7 rows. Walk me through how you'd debug.

- **Model answer.** Open the lesson folder. First, manually run the SQL in DBeaver against `db.sqlite` — does it actually return 5 or 7? If 5, the README is stale (edit it). If 7, then `check_examples.py`'s row-count reporting may have hit the multi-statement fallback and reported the wrong statement's count (see `check_examples.py:72-80` — last row-returning statement wins). Open the SQL: is it multi-statement? If yes, count manually statement by statement. Root cause likely one of: (a) CSV was edited without README update, (b) SQL was edited without README update, (c) harness reporting confusion on a multi-statement file. Fix the underlying state, not the harness output.
- **Follow-ups.** "How would the snapshot-test approach from the elevation roadmap have prevented this?" / "What's the right thing to do when the harness and a README disagree on truth?"
- **Weak answer.** "Trust the harness" — the harness only verifies parse, not correctness.

## Round 5 — production pushbacks (senior-level pressure)

### Q5.1 — Your course reaches 10,000 learners. Three of them open issues a week saying "this query gives different results in MySQL". What do you do?

- **Model answer.** Triage: are the differences (a) genuine dialect divergences (e.g. `||` works in SQLite + Postgres but not MySQL without `PIPES_AS_CONCAT`), (b) actual bugs in the lesson, or (c) the learner setting up MySQL wrong? Most will be (a). Action: document the divergences in a "Portability notes" footer per lesson, generated from a CI lane that runs the SQL against MySQL via `testcontainers`. Don't try to make every query work in every engine — the course teaches a dialect-aware mental model, not a least-common-denominator one. The lesson 12 example 06 already models the right answer for this kind of issue (explicitly contrasts SQLite vs Postgres).
- **Follow-ups.** "What if learners want a 'choose your engine' toggle at the top of every README?" / "Is it your job as a teacher to be honest about which engines you've tested?"

### Q5.2 — A new SQLAlchemy 2.1 release breaks `engine.begin()` semantics in some edge case. Your `<2.1.0` pin protects you for now. What's your long-term plan?

- **Model answer.** Pin protects from auto-breakage; doesn't free you from staying current. Plan: (a) subscribe to SQLAlchemy release notes; (b) when 2.1 drops, run the suite against it on a side branch, identify any failures, file an issue if it's an upstream regression or update the loader if the semantics genuinely changed; (c) bump the upper bound to `<2.2.0` and release. The principle is "pins are a circuit breaker, not a freeze" — they protect today's user, but maintenance must continue. The bigger risk is **silent stagnation** — a pin nobody revisits.
- **Follow-ups.** "How do you balance maintenance overhead against the risk of an unmaintained pin?" / "What automation would help here — Dependabot?"

### Q5.3 — A learner says they finished all 22 lessons but "still can't do SQL at work". What do you tell them?

- **Model answer.** Honest answer: the course teaches `SELECT`-only reading and writing of basic-to-intermediate queries against well-shaped schemas. It does **not** teach schema design, writes (INSERT/UPDATE/DELETE), transactions, performance reasoning, `EXPLAIN`, indexes, dialect-specific differences, ETL, or recursive CTEs. If "SQL at work" requires any of those (which it almost certainly does for a backend engineer), the learner needs the next layer of resources. Point them at "Use the Index, Luke!" for performance, the elevation roadmap's "pedagogical depth" section for the gap analysis, and concretely suggest hands-on practice on LeetCode-DB or StrataScratch to get writing-from-blank-page reps. The course is a strong foundation, not a complete preparation — that's a fair description, not a failure.
- **Follow-ups.** "If you could only add one missing topic to make the course more 'work-ready', what would it be?" / "How would you signal these gaps in the README so learners set expectations correctly upfront?"
