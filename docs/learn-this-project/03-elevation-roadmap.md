# Elevation Roadmap — `learn_sql_query_basic`

> Where would a senior engineer invest if they had 3–6 more months on this course? This doc is honest: the project is in **good shape for what it is** (a beginner SQL tutorial), so most "elevations" here are about turning a working tutorial into a more durable, distributable, and assessable teaching product — not papering over flaws.

## Executive view — the 5 highest-leverage upgrades

1. **Pytest-based test suite + expected-output snapshots.** The current harness (`examples/check_examples.py`) verifies that SQL parses, not that it produces the right answer. Snapshot the expected result rows and assert equality. This is the single biggest jump in test signal.
2. **GitHub Actions CI.** Run `check_examples.py` (and the new pytest suite) on every push. Without CI, a broken SQL or stale `db.sqlite` lands silently.
3. **Cross-engine verification (Postgres + SQLite).** The course teaches "ANSI SQL" but tests on SQLite only. Lesson 12's example_06 explicitly notes that "PostgreSQL is stricter than SQLite" — so the course already cares about portability, but the test harness doesn't enforce it. Add a Postgres run.
4. **Exercise mode — questions without given answers.** Every lesson currently shows the answer in `example_NN.sql`. There is no "your turn" component. Add a separate `exercises/` block per lesson with prompts whose answers the learner writes themselves, with hidden checks.
5. **Published as a package / website.** Right now the course is "clone the repo and read folders". A static site (mkdocs / Astro) or even a packaged uv-installable CLI (`learn-sql-query <lesson-number>` opens the lesson) would dramatically lower the entry friction and make the work portfolio-visible.

## Upgrade areas

### A) Test depth and coverage

**Current state.**
- `examples/check_examples.py` walks every lesson, runs every `example_*.sql`, prints OK/ERR with row count, exits non-zero on any error.
- This catches: SQL that doesn't parse; missing tables; FK column-name typos; references to a column that doesn't exist after a CSV edit.
- This **does not** catch: SQL that returns wrong rows; SQL whose result order differs from what the README implies; CSV→SQLite regeneration that produces a different schema; cross-engine portability.

**Senior-engineer target state.**

- A `tests/` directory at the repo root with `pytest` as the runner.
- For each `example_NN.sql`, an expected-rows snapshot (one JSON or CSV file per query) auto-asserted with `pytest --snapshot-update` to regenerate.
- A separate test that runs `gen_db.py` for each lesson in a temp dir and asserts the schema + row counts match the committed `db.sqlite`.
- A separate test that re-runs each SQL against Postgres-loaded equivalents of the same CSVs (see § C below).

**Alternatives.**

- *Approach 1: golden-file snapshots* (recommended). Run the SQL, dump rows to a stable representation (sorted, JSON-stringified), diff against committed snapshot. Pros: catches regressions. Cons: any intentional CSV edit churns lots of snapshot files — needs `--snapshot-update` discipline.
- *Approach 2: doctest-style inline expected results in the SQL file itself.* Append `-- expected: 5 rows; first row: (cat, 12)` to each file. Pros: zero new infra. Cons: SQL files become noisy; hard to diff structured rows in a comment.
- *Approach 3: a separate verification YAML per lesson* (`expected_results.yml`) listing `{file, n_rows, first_row, last_row}` per SQL file. Pros: structured, terse. Cons: bespoke format the harness must parse — `pytest` + snapshot lib is more standard.

**Knowledge prerequisites.**

- `pytest` fundamentals: `@pytest.fixture`, `@pytest.mark.parametrize`, test discovery.
- A snapshot library — `syrupy` is the modern Python choice; `pytest-regressions` is the more mature alternative.
- How to design idempotent fixtures (deleting & rebuilding `db.sqlite` in a per-test tmp dir).

**Suggested learning path.**

1. Read the [pytest Getting Started](https://docs.pytest.org/) → write 1 trivial test per lesson, parametrized over `glob("examples/**/example_*.sql")`.
2. Read the [syrupy README](https://github.com/syrupy-project/syrupy) → swap in snapshot assertion for one lesson, watch the snapshot file appear.
3. Convert all 22 lessons; add a CI step that fails when snapshots are missing.

### B) CI / CD maturity

**Current state.**
- No CI. No `.github/workflows/`. No Jenkins, no GitLab CI, no anything. The repo relies entirely on the author running `check_examples.py` locally before committing.

**Senior-engineer target state.**

- GitHub Actions workflow that on every push and PR:
  - Installs mise → installs Python 3.12 + uv → `uv sync --all-extras`.
  - Runs `pytest` (the upgraded test suite from § A).
  - Runs `check_examples.py` (as a smoke test that the snapshot suite doesn't replace).
  - Runs a markdown-link checker against `examples/README.md` + every lesson README to catch broken inter-lesson links.
  - Caches the `.venv` and the mise downloads for speed.

**Alternatives.**

- *Pre-commit hooks instead of CI:* run the test locally before commit. Pros: instant feedback. Cons: only catches what the author runs; collaborators bypass it.
- *Single `make verify` target instead of pytest:* lower setup cost. Cons: less standard, harder to integrate with downstream tools (codecov, etc.).

**Knowledge prerequisites.**

- GitHub Actions YAML syntax: jobs, steps, matrix builds, caching.
- How to install mise inside a GitHub runner (there's a community action `jdx/mise-action`).
- How to combine pytest + mise-managed Python in one workflow file.

**Suggested learning path.**

1. Read [GitHub Actions docs — Python starter workflow](https://docs.github.com/en/actions/automating-builds-and-tests/building-and-testing-python).
2. Read `jdx/mise-action` README on GitHub.
3. Implement minimal workflow that only runs `check_examples.py`; iterate to add pytest + caching.

### C) Cross-engine portability

**Current state.**
- The course teaches "ANSI SQL", and `examples/12-group-by/example_06.sql:14-22` explicitly contrasts SQLite's lenience with PostgreSQL's strictness. But every SQL is only **tested** against SQLite. If a lesson accidentally uses a SQLite-only function (`||` for string concat is in ANSI; `strftime` is SQLite-specific — both appear in lesson 10), the learner who later applies the same query in Postgres will hit a wall.

**Senior-engineer target state.**

- Optional pytest fixture that spins up Postgres via `testcontainers` (Docker-based) and re-loads each lesson's CSVs into it.
- Each `example_*.sql` runs against both SQLite and Postgres; cross-engine differences are flagged (some are intentional — e.g. SQLite uses `||` for concat, Postgres also accepts `||`).
- The README for each lesson grows a "Portability notes" footer documenting where SQLite differs from Postgres/MySQL.
- Alternatively (cheaper): run the suite against `sqlite3` + DuckDB; DuckDB is stricter than SQLite for `GROUP BY` and gives better error messages.

**Alternatives.**

- *Three-engine matrix (SQLite + Postgres + MySQL):* the full ANSI test. Pros: real portability proof. Cons: 3x CI runtime, 3x flakiness.
- *DuckDB alone:* DuckDB is the modern "strict SQLite". Lower infra cost than Postgres (no container needed). Cons: not a real production engine — learners don't deploy DuckDB.
- *Document portability in prose only:* cheapest. Cons: prose drifts from reality.

**Knowledge prerequisites.**

- Knowing the actual ANSI-vs-dialect differences: `strftime`/`date_trunc`, `||`/`CONCAT`, integer division (`/` returns int in some dialects, real in others), empty-string-vs-NULL handling.
- `testcontainers-python` basics.
- (For DuckDB path) the DuckDB Python API.

**Suggested learning path.**

1. Read Markus Winand's [Modern SQL](https://modern-sql.com/) — the canonical guide to standard-vs-dialect SQL.
2. Read [DuckDB Python docs](https://duckdb.org/docs/api/python/overview) — try loading one lesson's CSVs.
3. Pick one lesson (lesson 10 — built-in functions — is the obvious candidate) and run its SQL against DuckDB; document every divergence.

### D) Exercises (your-turn mode)

**Current state.**
- Every `example_NN.sql` contains the full answer. There is no "now you try" prompt anywhere in the curriculum. A diligent learner builds intuition; a passive learner copy-pastes.

**Senior-engineer target state.**

- Each lesson gains an `exercises/` subfolder with `exercise_01.sql` (prompt-as-comment, blank body) and a checker (`pytest test_exercises.py`) that loads the learner's SQL and asserts the result row-set matches a hidden golden.
- A small CLI (`learn-sql check examples/12-group-by/exercises/exercise_01.sql`) gives the learner instant feedback without leaving the editor.
- Hints are progressive — first hint reveals the SQL shape, second reveals the join keys, last reveals the answer.

**Alternatives.**

- *Quiz questions only (no graded code):* lighter — the quiz skill covers this. Cons: a learner can read a question and never type SQL.
- *Embedded notebook (`.ipynb`) per lesson:* a learner runs cells, sees output. Cons: notebooks are heavier infra, harder to git-diff.
- *External platform (LeetCode/StrataScratch/SQLZoo style):* outsource exercises entirely, link out. Cons: learners must context-switch.

**Knowledge prerequisites.**

- Designing exercises that map cleanly to the lesson's concept without sneaking in unrelated SQL.
- Hiding golden answers from the repo (separate `solutions/` branch, or `.gitignore`'d files generated from a script).
- Writing graders that are robust to row-order and column-order variations.

**Suggested learning path.**

1. Pick one lesson (lesson 14 — INNER JOIN — is a sweet spot for exercises) and hand-write 2 exercises + hidden goldens.
2. Write a grader that ignores row order (uses `frozenset` comparison).
3. Iterate on hint progression — show one exercise to a beginner and watch where they get stuck.

**Current state.**

**Senior-engineer target state.**

**Alternatives.**

**Knowledge prerequisites.**

- mkdocs Material or similar SSG: basic config, theme, navigation tree.
- Optional: SQL.js for in-browser SQLite execution.
- For the CLI: `click` or `typer` (Python CLI builders); how to package a uv-installable tool.

**Suggested learning path.**

1. Set up mkdocs Material locally; symlink `examples/` content into `docs/`; verify the site renders.
2. Add a custom navigation that mirrors the curriculum order.
3. (Optional) integrate SQL.js for the "run this query right here" button.

### F) Pedagogical depth — beyond syntax

**Current state.**
- The course covers `SELECT`-only syntax. It does not cover: index basics, `EXPLAIN`/`EXPLAIN ANALYZE`, transactions, isolation levels, normalization, schema design, performance tuning, recursive CTEs (a follow-on to lesson 20), `LATERAL` joins (a follow-on to lesson 19), or window-function frame specifications beyond cumulative sums.

**Senior-engineer target state.**

- A "part 2" curriculum (`examples-advanced/`) covering: `EXPLAIN` reading, B-tree indexes, recursive CTEs (factorials, tree traversal, graph paths), `LATERAL` joins, advanced window frames (`RANGE` vs `ROWS`, exclusion clauses), JSON columns, full-text search.
- A "performance lesson" that shows a slow query, runs `EXPLAIN`, adds an index, re-runs `EXPLAIN`, shows the improvement.

**Alternatives.**

- *Stay SELECT-only and call it done:* the current scope is honest and tight. Adding "part 2" risks bloating into the territory of "Use the Index, Luke!" and "SQL Performance Explained" without competing well.
- *Add only advanced SELECT (recursive CTEs, LATERAL, window frames):* tightly scoped. Cons: a learner who finishes still has no `EXPLAIN` literacy.
- *Add only performance lessons:* makes the course an interview-prep tool. Cons: doesn't help working analysts.

**Knowledge prerequisites.**

- For the inheritor: index internals (B-tree vs hash); SQLite's query planner peculiarities; how Postgres `EXPLAIN ANALYZE` output reads.
- Familiarity with recursive CTEs in SQLite, Postgres, and the SQL standard.

**Suggested learning path.**

1. Read Markus Winand's [Use the Index, Luke!](https://use-the-index-luke.com/) — the canonical free index primer.
2. Read the [SQLite EXPLAIN docs](https://www.sqlite.org/eqp.html).
3. Pick one lesson's dataset, scale it 100x via CSV repetition, and watch query times before/after adding an index.
