# Lesson 21 — 集合运算（UNION / INTERSECT / EXCEPT）

> 两张表分别记录了"堂食"和"外带"的订单。怎么把这两份结果"拼起来"、"取交集"、"取差集"？这节课就讲这件事。

## 我们要学什么

到目前为止我们处理的都是"一个 SELECT 返回一份结果"。
这节课要学的是**把两个 SELECT 的结果拼成一份**——四种最常见的拼法：

| 构件 | 一句话 |
|------|--------|
| `UNION ALL` | 上下两份结果**直接堆起来**，重复的也保留 |
| `UNION` | 上下两份结果堆起来，**去掉重复行** |
| `INTERSECT` | 只留下**两边都出现**的行（交集） |
| `EXCEPT` | 只留下**第一份里有、第二份里没有**的行（差集） |

集合运算的本质是把两个 SELECT 的**结果集**当成数学上的"集合"来加减。
它的最大优势是：当你只关心"这一列在两个查询里是否同时出现"时，比 JOIN / 子查询 都写起来更直接、更短、更接近自然语言。

但它有一条**硬规则**：参与拼接的两个 SELECT 必须返回**相同数量、相同顺序、类型相容**的列——SQLite 是按**位置**配对的，**不看列名**。最后一个 example 会专门讲这条规则。

## 数据库故事

这节课的场景是一家小咖啡馆，订单分两条线记录：

| 表名 | 内容 | 行数 |
|------|------|------|
| `dine_in_orders` | 堂食订单（`order_id`, `customer_email`, `items_total`, `ordered_at`, `table_number`） | 30 |
| `takeout_orders` | 外带订单（`receipt_id`, `customer_email`, `items_total`, `ordered_at`, `pickup_time`） | 30 |

两张表**没有外键关系**——它们各自独立记录两条业务线。但因为同一位顾客可能既会堂食、也会外带，所以 `customer_email` 这一列在两张表里**会有重叠**，这正是集合运算大显身手的地方。

> 注意一个**故意的小坑**：两张表里"主键"叫的名字不一样（一个叫 `order_id`，一个叫 `receipt_id`），其它列名虽然写法相似，但语义略有不同（`table_number` vs `pickup_time`）。这是真实业务里非常常见的——两个系统各自演化出来，列名不会齐整地对上。集合运算遇到这种情况，就需要你**用 AS 把两边的列对齐**。

## 先自己探索一下

正式开始前，**强烈建议你先自己动手点一点**：

- 在 DBeaver 左侧栏里展开 `dine_in_orders` 和 `takeout_orders`，双击预览数据。
- 对照看两张表的列：哪些列名相同？哪些不同？类型分别是什么？
- 随便挑一个出现频率高的邮箱（比如 `emma.larsson@gmail.com`），在两张表里都过滤一下，看看她是不是两边都点过单。
- 心里大概估一下：**完全只堂食、只外带、又堂食又外带**的客人各有多少？

这些预判会让后面的 INTERSECT / EXCEPT 结果一出现你就立刻"认得"——而不是被一堆邮箱晃花眼。

## 关于 SQL 注释（小知识）

你会发现每个 example 文件里都有一大堆以 `--` 开头的文字。
SQL 有两种注释写法：

```sql
-- 单行注释：从 -- 到这一行结尾的内容都被数据库忽略。

/*
 * 块注释：可以跨多行。
 * 写长一点的说明很方便。
 */
```

数据库**会直接忽略**注释，所以你随便写，**不会影响**查询结果。
我们在每个 example 文件里把"业务问题"和"为什么这么写"都用注释写在 SQL 旁边，
就是希望你以后回过头来看也能立刻想起这条 SQL 在干嘛——
注释和代码住在一起，比单独翻教程要省事得多。
