# Lesson 20 — CTE 公共表表达式（`WITH`）

> 当一个查询里出现了"先算 A，再用 A 算 B"的需求，CTE 让你像讲故事一样从上往下写 SQL。

## 我们要学什么

这节课的主题是 **`WITH ... AS (...)` 公共表表达式（CTE）**。它解决一个非常具体的痛点：当你需要在查询里复用一个"中间结果"时，写嵌套子查询会让人头大，而 CTE 让查询读起来像写作文。

我们会练这几件事：

| 构件 | 一句话 |
|------|--------|
| 单个 CTE | 给一个中间结果起个名字，再在主查询里用 |
| 多个 CTE | 用逗号连接，一个查询里串好几步 |
| 子查询 → CTE 重构 | 把"嵌套到看不懂"的写法翻成"自上而下"的写法 |
| CTE + 回连基础表 | CTE 算完中间表，最后再 JOIN 回原表出报表 |

> 小提示：SQL 里还有 `WITH RECURSIVE` 可以写递归查询（比如组织结构层级展开），那是进阶话题，本课不涉及。

## 数据库故事

这节课的练习数据是一个**房地产中介系统**：经纪人挂房、客户成交、报表口径。

| 表名 | 内容 | 行数 |
|------|------|------|
| `agents` | 经纪人信息（姓名、所属经纪公司、入职日期） | 10 |
| `listings` | 在售房源（地址、社区、卧室数、挂牌价、状态：active/pending/sold/withdrawn） | 40 |
| `transactions` | 成交记录（成交价、过户日期、买家姓名） | 20 |

外键关系：`listings.agent_id → agents.agent_id`，`transactions.listing_id → listings.listing_id`。

注意：**并非每个 `status = 'sold'` 的房源都有对应的 `transactions` 记录**（财务还没走完流程），而 `withdrawn` 的房源更是**一定没有**成交记录。这正是 CTE 例子能玩出花样的地方。

## 先自己探索一下

正式开始前，**强烈建议你先自己在 DBeaver 里点一点**：

- 把三张表都预览一下，看看 `agents`、`listings`、`transactions` 的列分别长什么样。
- 注意 `listings.status` 有哪几种取值（active / pending / sold / withdrawn）。
- 数一下：`status = 'sold'` 的房源有几条？`transactions` 又有几条？两者数量不一样——想一想为什么。

这种"先看数据再写 SQL"的肌肉记忆很重要——写 CTE 之前先知道每张表大概什么形状，写起来就有画面感。

## 关于 SQL 注释（小知识）

你会发现每个 example 文件里都有一大堆以 `--` 开头的文字。
SQL 有两种注释写法：

```sql
-- 单行注释：从 -- 到这一行结尾的内容都被数据库忽略。

/*
 * 块注释：可以跨多行。
 * 写长一点的说明很方便。
 */
```

数据库**会直接忽略**注释，所以你随便写，**不会影响**查询结果。
我们在每个 example 文件里把"业务问题"和"为什么这么写"都用注释写在 SQL 旁边，
就是希望你以后回过头来看也能立刻想起这条 SQL 在干嘛——
注释和代码住在一起，比单独翻教程要省事得多。
